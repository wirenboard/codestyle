Требования к сервисам контроллера

*С этой инструкцией нужно сверяться при создании нового сервиса или изменении существующего. [Пример оформления](https://github.com/wirenboard/wb-python-service-template) сервиса на python.*

1. **Запуск**  
* Чтение конфиг-файла. Если согласно конфигу от сервиса ничего не требуется (например, в mbgate выключены все топики и т.п), то он завершается с EXIT\_NOTRUNNING=7. Если конфиг поврежден — EXIT\_NOTCONFIGURED=6. Исключение: если у сервиса есть функционал (RPC/FastAPI-эндпоинты), работа которого не зависит от конфигурации, то сервис должен сообщить в логе о результатах чтения конфига и продолжить работать.  
* Подключение к брокеру mosquitto. В обработчике события подключения сервис подписывается на нужные топики, публикует свои rpc-эндпоинты.  В случае неудачной аутентификации завершается с EXIT\_INVALIDARGUMENT=2 без перезапуска в systemd. В иных случаях неудачи (например, брокер недоступен) продолжает попытки подключиться.  
* Все контролы публикуются по внутренней [конвенции](https://github.com/wirenboard/conventions). Работа с rpc организуется согласно [правилам](https://github.com/wirenboard/mqtt-rpc).  
* Сервис должен уметь запускаться без флагов, по умолчанию используются пользовательские настройки из /etc/ИМЯ\_СЕРВИСА.conf. У сервиса должен быть флаг \-c для запуска с альтернативным конфигом. См ниже Работа с конфигурацией.  
    
2. **Обработка событий** **системы**  
* Перезапуск брокера. Сервис не падает, не зависает, пытается установить подключение заново. После подключения заново подписывается, публикует rpc-эндпоинты, перепубликовывает мета-данные и последние значения контролов (рекомендуется это делать в событии подключения к брокеру).  
* Сигналы SIGTERM, SIGINT. Завершает работу c EXIT\_SUCCESS=0. Публикует пустые retain-сообщения во все свои топики, отключается от брокера. Eсли брокер недоступен во время завершения, записать ошибку в журнал, код выхода должен быть так же EXIT\_SUCCESS=0.  
* Потеря связи с внешним сервисом. Пытается установить подключение заново.

3. **Завершение работы, коды возврата**  
   *За основу взяты [рекомендации freedesktop](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#Process%20Exit%20Codes). Использовать другие коды из рекомендации допускается, но лучше ограничиваться списком ниже.*  
     
* EXIT\_SUCCESS=0 \- успешное завершение (не имеет смысла в контексте долгоживущего сервиса, подходит для oneshot). Для обычных сервисов см. EXIT\_NOTRUNNING=7  
* EXIT\_FAILURE=1 \- общая ошибка при неудачном завершении работы сервиса, есть смысл перезапустить сервис  
* EXIT\_INVALIDARGUMENT=2 \- неверные или лишние аргументы командной строки, автоматически перезапускать сервис бессмысленно  
* EXIT\_NOTCONFIGURED=6 \- неверная конфигурация (когда конфиг плохо распарсился или в нём есть логические ошибки), автоматически перезапускать сервис бессмысленно  
* EXIT\_NOTRUNNING=7 \- согласно конфигурации, сервису не надо ничего делать, потому он выключился и не потребляет ресурсов, при этом он не failed

4. **Оформление в systemd**

При неудачном завершении сервиса со статусом EXIT\_FAILURE=1 должна производиться попытка повторного запуска. EXIT\_NOTRUNNING=7 должен быть настроен как успешный, а остальные коды возврата настраиваются для предотвращения повторного запуска сервиса.  
Если сервис должен иметь автозапуск, необходимо оформить секцию Install

```sh
[Service]
...
Restart=on-failure
RestartSec=<Время ожидания перед перезапуском службы, сек>
RestartPreventExitStatus=2 6
SuccessExitStatus=7
...	
[Install]
WantedBy=multi-user.target

```

5. **Работа с конфигурацией**  
* Пользовательские настройки сервисов хранить в /etc/ИМЯ\_СЕРВИСА.conf в формате JSON. Дополнительные настройки, которые представляют собой отдельные файлы, хранить в каталоге /etc/ИМЯ\_СЕРВИСА.conf.d/.  
* Если нужны настройки, недоступные для редактирования пользователем (например, параметры, определяемые аппаратными характеристиками), то их нужно разместить в файлах в каталоге /var/lib/ИМЯ\_СЕРВИСА/conf.d. Файлы должны быть генерируемыми.  
* Если нужны какие-то части конфигурации, которые приезжают с пакетами в готовом виде, но не должны редактироваться, их надо хранить в /usr/share.  
* Все файлы настроек не должны конфликтовать между собой, тк для получения итоговой конфигурации они должны сливаться в один конфиг.  
* Корректность структуры и содержания файлов настроек проверять автоматически (например, через JSON-валидатор и JSON-схему, Pydantic и т.п), это избавит от сложного кода проверки корректности в сервисе. Если настройки редактируются в веб\-интерфейсе, то при установке пакета схему размещать в /usr/share/wb-mqtt-confed/schemas (если схема статическая) или в /var/lib/wb-mqtt-confed/schemas (если схема генерируется сервисом в процессе работы и может меняться). Правила составления JSON-схем смотри в [wb-mqtt-confed](https://github.com/wirenboard/wb-mqtt-confed).
